# 创序 OCC 数据库表设计

- 文档状态：待书面审阅（设计章节已确认）
- 日期：2026-07-28
- 数据库：PostgreSQL
- 关联文档：`创序OCC_技术选型与架构设计_2026-07-28.md`

## 1. 设计目标

数据库首先保证两项平台能力：

1. 业务可替换、可扩展：稳定平台表与版本化领域定义分离，领域字段采用 JSONB，但关键标识、版本、关系、状态和审计继续使用关系约束。
2. 完整策略授权：PostgreSQL 保存身份、统一实体、关系图和不可变策略版本，OPA 作为本地无状态决策面，支持平台基线、领域包和客户覆盖三层策略。

每个客户使用独立私有实例，不在业务表中增加 `tenant_id`。单实例仍保留 `platform.instance`，用于部署身份、配置版本和审计来源，不用于实现多租户。

## 2. 核心决策

- 使用“强类型核心表 + JSONB 领域对象 + 可重建类型化索引投影”。
- 所有可授权主体和资源统一登记在 `authz.entity`。
- 主体、角色、组、流程、任务、证据及领域对象使用同一实体 ID 空间。
- 关系事实统一保存在 `authz.relationship`，不为组成员、角色授予等场景另建重复事实表。
- 完整策略由 OPA/Rego 执行；任何适用 `DENY` 覆盖 `ALLOW`，无命中默认拒绝。
- 平台基线 `DENY` 不可被领域包或客户管理员覆盖。
- 每条领域业务记录绑定创建时的 schema 版本，升级必须显式迁移。
- Flowable 私有表由 Flowable 管理，OCC 表只保存引擎标识，不对 Flowable 表建立外键。
- 每个客户实例只有一个活动 embedding 空间；新空间重建完成后原子切换。
- 不使用 PostgreSQL RLS 表达动态领域授权，避免与 OPA 形成两套授权真相。

## 3. Schema 划分

| Schema | 职责 | 数据库账号 |
| --- | --- | --- |
| `platform` | 实例身份、系统版本和受控配置 | Core 读写 |
| `catalog` | 领域包、类型、动作、关系、表单和规则定义 | Core 读写，AI 只读受限视图 |
| `iam` | 用户、组、服务账号、角色和外部身份 | Core 读写 |
| `authz` | 统一实体、关系、策略、发布和决策日志 | Core 读写，OPA 通过 bundle/API 获取 |
| `occ` | 业务对象、流程投影、任务、证据、风险和资源 | Core 读写 |
| `audit` | 审计、幂等和 Outbox | Core 读写，审计账号只读 |
| `ai` | 模型、Agent、知识、向量、运行、建议和会话 | Core 管理可授权元数据；AI 读写运行与索引子表 |
| `flowable` | Flowable 引擎私有表 | Flowable/Core 事务账号 |

生产数据库至少使用 Core、AI、迁移和只读审计四类最小权限账号。AI 账号不能读取 `flowable`、`iam` 凭据或 OCC 私有表。

## 4. 通用约定

### 4.1 类型与命名

- 表和列使用 `snake_case`。
- 主键使用应用生成的 UUIDv7。
- 时间使用 `timestamptz`，统一写入 UTC。
- 金额和成本使用 `numeric`，不使用浮点数。
- 可扩展代码使用 `text + FK/检查约束`，不使用 PostgreSQL enum。
- JSON 字段必须是对象时添加 `CHECK (jsonb_typeof(column) = 'object')`。
- 密钥只保存外部密钥系统引用 `secret_ref`，不保存明文。

### 4.2 通用可变列

可变聚合默认采用以下基础列。各表字段字典已经单列 `id` 时，“通用可变列”仅指 `row_version` 和创建/更新审计列，不重复增加主键。

```text
id UUID PRIMARY KEY
row_version BIGINT NOT NULL DEFAULT 0
created_by UUID NULL
created_at TIMESTAMPTZ NOT NULL
updated_by UUID NULL
updated_at TIMESTAMPTZ NOT NULL
```

除平台初始化种子外，`created_by` 和 `updated_by` 必须引用 `iam.principal(id)`。更新必须使用 `WHERE id = ? AND row_version = ?`，成功后将 `row_version + 1`。

### 4.3 删除规则

- 外键默认 `ON DELETE RESTRICT`。
- 业务事实通过归档、撤销或失效时间退出活动状态。
- 只有未发布草稿子项、上传临时记录等纯从属数据允许级联删除。
- 审计、证据版本、策略发布和 AI 运行记录只追加，不原地改写。

活动关系使用部分唯一索引 `(relation_definition_id, subject_entity_id, object_entity_id) WHERE revoked_at IS NULL`。更新关系通过撤销旧行并新增行表达，不覆盖历史来源。

### 6.6 `authz.authorization_state`

单行授权版本闸门，包含 `id`、`current_revision` 和 `updated_at`。普通业务写命令首先对该行取得共享锁；关系、策略 release 或 `auth_attributes` 变更取得排他锁并在提交前递增 `current_revision`。这使撤权与业务写入严格串行，避免旧权限快照在撤权后仍然提交。

当前规模接受授权事实变更的全局排他锁。若未来授权属性写入频率成为瓶颈，再按组织或资源域拆分 scoped authorization state；首版不提前引入该复杂度。

### 6.7 `authz.relationship_closure`

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `relation_definition_id` | `uuid` | 传递关系定义 |
| `ancestor_entity_id` | `uuid` | 上级/容器 |
| `descendant_entity_id` | `uuid` | 下级/成员 |
| `depth` | `integer` | 路径长度 |
| `build_revision` | `bigint` | 构建时的 `authorization_state.current_revision` |

该表是可重建投影，只用于候选过滤和查询加速，不能作为 OPA 的最终放行事实。最终决策始终使用直接关系；过期闭包最多增加无效候选或造成保守漏选，不能造成越权放行。

### 7.4 `authz.policy_release` 与 `policy_release_item`

| 列 | 类型 | 说明 |
| --- | --- | --- |

## 12. 写事务与授权顺序

改变业务状态的命令使用以下顺序：

1. 开启数据库事务。普通业务写对 `authz.authorization_state` 取得共享锁；会改变关系、策略或授权属性的命令取得排他锁。
2. 读取目标实体、直接关系、active policy release、授权 revision 和业务 `row_version`。
3. 在同一事务快照内构造 `principal/action/resource/context` 输入并调用本地 OPA。
4. OPA 不可用、返回错误或 release/revision 不一致时默认拒绝。
5. 检查客户端 `expectedVersion`。
6. 执行 Flowable 和 OCC 业务更新，并同步授权属性、关系、审计和 Outbox；授权事实有变更时递增 authorization revision。
7. 提交事务后失效 Redis 并异步发布 Kafka。

这样避免“检查时有权，提交时权限已变化”的竞态。被拒绝的决策不产生业务事务，但必须在独立追加事务中写入 `decision_log`。

## 14. 故障与错误语义

- JSON Schema 校验失败：`422`，不写业务数据。
- 唯一约束或幂等键请求哈希冲突：`409`。
- `row_version` 不匹配：`409` 并返回当前版本摘要。
- OPA 不可用、策略 revision 不一致或决策错误：默认拒绝，写命令不执行。
- 策略编译、测试或审批失败：bundle version 保持非发布状态。
- Kafka 不可用：业务事务正常提交，Outbox 保留重试。
- Redis 不可用：回源 PostgreSQL，不影响授权和写事务。
- 对象存储不可用：上传保持待确认，不创建有效证据/文档版本。
- embedding 重建失败：保持旧活动空间。
- 数据迁移单项失败：对象保持旧 schema 版本，可重试。

## 15. 迁移、备份与治理

- Core schema 使用 Flyway；迁移脚本只前进，不依赖运行时自动回滚。
- Flowable schema 升级与 Core 迁移在兼容性验证后作为一个发行变更执行。
- 领域包只写版本化定义和数据，不执行数据库迁移。
- 发布前从上一发行版备份恢复并执行完整升级演练。
- 用户注销时移除认证凭据并按保留策略匿名化个人字段，审计 ID 和证据链保留。
- 消息、AI 输入输出、知识原文、决策日志和审计分别配置保留期。
- 到期删除和对象存储清理必须产生治理审计。

## 16. 测试门禁

1. 从空库执行全部 Flyway 与 Flowable 迁移。
2. 从上一发行版备份执行升级并验证数据不变量。
3. 测试共享主键、组合 FK、关系两端类型、基数、环检测、活动唯一性和删除限制。
4. 属性测试默认拒绝、DENY 优先、平台 DENY 不可覆盖和随机关系图无越权。
5. 测试关系撤销、策略切换、授权属性变更与业务写命令并发，确认 authorization state 锁不会产生 TOCTOU 越权。
6. 测试同对象并发更新、幂等键重用、Outbox 重投、资源预约和 schema 迁移重试。
7. 测试未授权文档不会进入 RAG 候选 chunk 集合。
8. 测试 embedding 新空间构建、评测、切换和失败回滚。
9. 对关键查询执行 `EXPLAIN (ANALYZE, BUFFERS)` 并保存计划基线。
10. 演练备份恢复、策略回滚、分区归档和对象存储引用清理。

## 17. 实施前验证门禁

1. 用最小原型验证 Spring 事务中 Flowable、OCC 投影、审计和 Outbox 原子提交。
2. 验证事务内本地 OPA 调用在目标硬件上的 p95 延迟与连接失败行为。
3. 验证 OPA 三层 bundle 的签名、加载确认、revision 匹配和回滚。
4. 用用户-组-角色-项目-任务关系样例验证关系图、闭包和批量授权。
5. 用两个 schema 版本验证 JSONB 对象显式迁移及索引投影重建。
6. 用一套真实知识文档验证“先授权文档，再执行混合检索”。
