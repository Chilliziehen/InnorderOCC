# 创序 OCC 技术选型与架构设计

- 文档状态：待书面审阅（设计章节已确认）
- 日期：2026-07-28
- 适用阶段：首个 16 周 MVP 及后续领域扩展基线
- 关联文档：`创序OCC_项目企划书(1).docx`

## 1. 决策摘要

创序 OCC 采用“确定性流程控制面 + 概率智能面”的双轨架构。标准 BPMN 流程由 Flowable 直接执行，核心业务状态只能由 Kotlin/Spring Boot 服务在 PostgreSQL 事务中推进。Node.js/LangChain.js 负责理解、检索、规划、核验和风险建议，不得直接修改流程事实。

系统以每客户独立实例的方式私有部署。首个领域是嵌入式开发教学，但核心架构不绑定学校或教学基础设施。跨领域扩展通过版本化领域包实现，不通过复制和修改核心服务实现。

选定技术基线：

| 层级 | 技术选择 | 主要职责 |
| --- | --- | --- |
| 桌面客户端 | Electron Forge、React、TypeScript、Vite、Ant Design | 学生、负责人和管理员工作台 |
| 流程建模 | bpmn-js | BPMN 编辑、查看和领域属性配置 |
| OCC Core | JDK 21、Kotlin、Spring Boot、Flowable 7.x | BPMN 执行、事务、权限、证据、审计和领域 API |
| AI Service | Node.js LTS、TypeScript、Fastify、LangChain.js、Zod | 多供应商模型接入、RAG 和 Agent 编排 |
| 结构化存储 | PostgreSQL、pgvector | 业务事实、流程数据、审计、Outbox 和向量索引 |
| 对象存储 | S3 兼容存储，默认支持 MinIO | 证据文件和知识源原件 |
| 事件骨干 | Apache Kafka，KRaft 模式 | 跨服务领域事件和异步扩展 |
| 缓存与实时状态 | Redis | 可重建读缓存、AI 缓存、限流和在线状态 |
| 身份认证 | Spring Security、内置账号、OIDC | 本地试点账号和企业身份平台接入 |
| 部署 | Docker Compose | 每客户独立私有实例 |

依赖版本在实施阶段的兼容性验证中固定到精确版本和锁文件。版本通道限定为 JDK 21 LTS、Flowable 7.x，以及与 Flowable 兼容的 Spring Boot 3.x；Node.js 使用当期 LTS。未经兼容性测试不得跨主版本升级。

## 2. 目标与范围

### 2.1 目标

1. 使用标准 BPMN 直接驱动流程执行，保证状态、依赖、权限和审计可验证。
2. 支持每客户独立私有部署，并允许接入客户已有数据库、对象存储、Kafka、Redis、OIDC 和模型服务。
3. 通过领域包快速替换流程、规则、角色、表单、证据要求和知识源。
4. 允许 AI 能力独立演进和横向扩展，同时确保 AI 故障不阻断核心流程。
5. 支持 Electron 全员桌面客户端，并提供断网时的只读缓存能力。

### 2.2 首版非目标

- 不实现单实例多租户。
- 不实现自动向政府或第三方高责任系统提交不可逆操作。
- 不自研 BPMN 执行引擎。
- 不把五类 Agent 拆成五个独立服务。
- 不提供完整离线写入和冲突合并。
- 不引入 Kubernetes、服务网格、独立搜索引擎或独立向量数据库。
- 不将 Kafka 用作业务事实主存储，也不采用事件溯源作为首版数据模型。

## 3. 备选方案与结论

### 3.1 方案 A：Flowable 嵌入式模块化平台，已采用

Flowable 嵌入 Kotlin/Spring Boot 核心服务，Node.js 独立承载 LangChain.js，Electron 提供统一客户端。该方案的 Flowable 核心采用 Apache 2.0 许可，可私有部署；流程事务和 OCC 领域事务可以在同一服务边界内协调，组件数量适合两名工程师维护。

主要代价是同时维护 JVM 和 Node.js 两个运行时，以及自行开发领域化工作台和 BPMN 属性面板。通过 OpenAPI、版本化事件 schema 和严格数据库边界控制该复杂度。

### 3.2 方案 B：Camunda 8 分布式编排平台，未采用

Camunda 8 具备成熟的分布式流程编排与运维能力，但 8.9 自托管生产使用需要企业许可，完整组件栈对当前团队和试点规模过重。未来只有在客户明确承担许可成本且出现大规模分布式编排需求时才重新评估。

### 3.3 方案 C：TypeScript 自研 BPMN 执行层，未采用

全 TypeScript 可减少语言数量，但定时器、并发网关、补偿、迁移、幂等、历史审计和异常恢复会成为自研责任。这些能力位于项目最要求确定性的控制内核，因此不接受该风险。

## 4. 总体架构

```text
Electron / React
       |
       | HTTPS: REST commands/queries, OIDC/JWT, SSE
       v
OCC Core: Kotlin + Spring Boot + Flowable
       |-- PostgreSQL: business + Flowable + audit + outbox
       |-- S3/MinIO: evidence and source files
       |-- Redis: rebuildable cache and ephemeral state
       |
       +-- Outbox Publisher --> Kafka
                                  |-- AI Service / LangChain.js
                                  |-- notification projection
                                  |-- cache invalidation
                                  `-- retrieval and analytics projections
```

架构遵循以下边界：

1. Electron 只调用 OCC 领域 API，不调用 Flowable 原生 API。
2. AI Service 只通过受限查询 API 获取上下文，通过受限命令 API 提交建议。
3. Kafka 消费者不能直接推进 Flowable 关键状态。
4. PostgreSQL 是结构化业务事实的唯一权威来源。
5. Redis 中的数据必须可丢失、可重建，Redis 故障不能阻断核心流程。
6. 对象存储中的文件只有在 Core 校验并提交元数据后才构成有效证据。

## 5. 服务与模块边界

### 5.1 Electron 客户端

同一安装包按权限展示参与者、负责人和管理员工作台。主要模块包括今日任务、流程地图、证据提交、审核队列、风险雷达、领域包建模和系统管理。

渲染进程启用 sandbox、context isolation 和 CSP，关闭 Node 集成。文件系统、更新、深链接和凭据操作仅由主进程执行，并通过有类型约束的 preload IPC 暴露最小接口。只读离线缓存不得接受业务写入；Core 不可连接时，所有变更操作明确禁用。

OIDC 通过系统浏览器完成，回调由受控深链接返回 Electron。令牌由主进程使用操作系统安全存储保护，不进入 renderer 的持久存储。

### 5.2 OCC Core

OCC Core 是模块化单体，至少包含以下边界：

| 模块 | 职责 |
| --- | --- |
| Identity & Access | 内置账号、OIDC 映射、角色与动作权限 |
| Domain Package | 草稿、校验、发布、版本、差异和迁移预演 |
| Process Definition | BPMN/DMN 部署及 Flowable 适配 |
| Process Instance | 实例生命周期、业务键和领域包版本绑定 |
| Task | 人工任务、候选人、领取、完成、退回和例外 |
| Evidence | 上传会话、元数据、哈希、版本和任务关联 |
| Risk | 风险规则、等级、升级对象、时限和处置状态 |
| Audit | 状态变化、人工覆盖、关键读取和配置变更 |
| Outbox | 事务内事件记录、发布进度和重试状态 |

Flowable 被封装在 Process Definition、Process Instance 和 Task 模块内部。其他模块不能依赖 Flowable 数据表或原生实体，只能使用内部领域接口。

### 5.3 AI Service

AI Service 是一个独立进程，内部包含规划、辅导、核验、风险和监督 Agent。Agent 共享模型适配、工具注册、结构化输出校验、RAG、追踪和评测设施，但不共享可变的私有业务事实。

LangChain.js 提供内置供应商和自定义供应商适配。每个供应商配置声明模型能力、数据发送策略、超时、并发、限流和成本元数据。模型不支持所需能力时，服务应拒绝执行，而不是降级为不可验证输出。

Agent 工具采用白名单，输入输出使用 Zod 校验。关键建议必须记录客户实例、模型、提示词版本、领域包版本、知识库版本、引用来源、工具调用和最终结构化结果。

## 6. 领域包设计

领域包是跨领域扩展的最小发布单元，包含：

- `manifest`：领域标识、语义版本、依赖、内容哈希和兼容范围。
- BPMN：流程、人工任务、服务任务、事件、网关和计时器。
- DMN：确定性准入、风险分级和条件判断。
- JSON Schema 表单：节点输入、审核和配置表单。
- 角色与权限：领域角色到 OCC 动作的映射。
- 证据规则：允许类型、大小、数量、哈希和验收条件。
- 风险规则：触发条件、等级、时限和升级对象。
- 知识源清单：来源、版本、访问策略和索引参数。
- UI 元数据：标签、排序、分组和领域展示信息。
- 回归场景：发布前必须通过的标准流程和规则样例。

领域包不允许携带任意可执行脚本、数据库迁移或密钥。扩展服务任务只能引用核心预注册的受控能力标识。

领域包状态为草稿、已校验、已发布、已废弃。已发布版本不可修改，并具有内容哈希。每个流程实例显式绑定领域包版本；发布新版本不会改变运行实例。运行实例迁移是独立操作，必须生成影响预览并经授权人员确认。

## 7. 数据与事件流

### 7.1 领域包发布

1. 负责人在 Electron 中编辑 BPMN、DMN、表单和领域配置。
2. Core 校验标准语法、引用完整性、禁用元素、权限和回归场景。
3. Core 生成版本差异、运行实例影响和知识索引计划。
4. 授权人员确认发布后，Core 固化领域包内容和哈希，并部署 Flowable 定义。
5. 后续新实例显式选择该版本；旧实例保持原版本。

### 7.2 业务命令

1. Electron 提交身份凭据、幂等键、`expectedVersion` 和业务输入。
2. Core 在同一数据库事务中完成鉴权、规则与 Flowable 执行、业务更新、审计和 Outbox 写入。
3. Core 返回已提交版本、状态和审计 ID。
4. Outbox Publisher 将事件至少一次投递到 Kafka。
5. AI、通知、缓存和分析消费者按事件 ID 幂等处理。

系统不承诺 PostgreSQL 到 Kafka 的端到端 exactly-once。正确性模型是 Transactional Outbox、至少一次投递、聚合内有序和消费者幂等。Kafka 分区键使用业务聚合 ID。

### 7.3 AI 建议

1. AI Service 消费需要智能处理的领域事件。
2. AI Service 使用最小权限 API 获取当前状态、领域包版本和允许发送的数据。
3. RAG 返回带版本来源，LangChain Agent 生成结构化建议。
4. 监督策略检查引用、权限、置信度和结构完整性。
5. AI Service 调用受限 Core 命令记录建议或创建人工队列项。
6. 只有规则、证据或人工批准可以推进关键流程状态。

### 7.4 证据上传

1. Electron 向 Core 申请短时上传许可。
2. Electron 直接上传对象存储，并提交客户端哈希。
3. Core 校验对象存在性、大小、类型和哈希。
4. Core 在事务中创建证据元数据和任务关联。
5. 未完成或未关联的对象由后台任务按保留策略清理。

## 8. Kafka 与 Redis 职责

### 8.1 Kafka

Kafka 仅承担跨服务领域事件。首版主题按稳定业务类别划分，事件携带事件 ID、schema 版本、客户实例 ID、聚合类型、聚合 ID、聚合版本、发生时间、关联 ID 和数据分类。

消费者短暂失败时指数退避；超过上限或遇到永久错误时进入死信主题和运维队列。Kafka 不可用只延迟 AI、通知、缓存失效和分析，不回滚已提交的核心业务。

试点部署允许单 broker KRaft 配置。正式生产按客户可用性目标选择 3 broker 或客户已有 Kafka 服务。单 broker 不宣称高可用。

### 8.2 Redis

Redis 支持三类能力：

1. 工作台读模型：雷达、计数和流程摘要，使用短 TTL 和事件驱动失效。
2. AI 与检索缓存：检索结果、模型能力探测、限流和可安全复用的结果。
3. 实时状态：在线连接映射、短期通知游标和临时状态。

AI 缓存键必须包含客户实例、领域包版本、知识库版本、模型供应商、模型名和提示词版本。禁止缓存流程准入结论、证据有效性、审批结果、权限判定结果和未提交状态。

Redis 不可用时，查询回源 PostgreSQL，在线状态和缓存能力降级，核心流程继续工作。系统不做 PostgreSQL 与 Redis 的双写事务。

## 9. 核心数据模型

| 实体 | 关键内容 |
| --- | --- |
| Organization Instance | 单套私有部署的组织配置和数据策略 |
| User / Role / Membership | 用户、领域角色、组织关系和身份映射 |
| Domain Package / Version | 领域资产、状态、哈希、兼容范围和发布记录 |
| Process Definition / Instance | Flowable 标识、业务键、领域包版本和生命周期 |
| Task | 类型、状态、负责人、候选人、期限和版本 |
| Evidence | 对象引用、类型、大小、哈希、提交人和验收记录 |
| Event | 状态变化、原因、关联 ID、操作者和发生时间 |
| Risk | 等级、规则、置信度、责任人、时限和处置结果 |
| Resource | 设备、场地、人员时段、容量和预约 |
| AI Run / Recommendation | 模型、提示词、来源、工具调用、结果和审核状态 |
| Audit Record | 操作者、动作、对象、前后版本、理由和时间 |
| Outbox Record | 事件载荷、schema 版本、发布状态和重试信息 |

Core 与 AI 使用独立 PostgreSQL schema 和数据库账号。AI 不得读取 Flowable 表或 Core 业务表，只能使用 OCC API 和授权事件。

## 10. API 与契约

- 同步命令和查询使用 HTTPS REST，OpenAPI 是 Electron、Core 和 AI 的契约来源。
- 状态变化命令使用幂等键；竞争对象使用 `expectedVersion`。
- 乐观锁冲突返回 `409 Conflict`，客户端必须刷新，不得静默覆盖。
- 错误响应使用 Problem Details，包含稳定错误码、重试属性、关联 ID 和用户可理解说明。
- 实时通知使用 SSE；可靠通知先持久化，再推送在线客户端。
- Kafka 事件使用带版本的 JSON Schema。CI 阻止未提供兼容策略的破坏性变更。
- Core API 不暴露 Flowable 原生对象、表名或内部状态编码。

## 11. 故障处理与降级

| 故障 | 系统行为 |
| --- | --- |
| 并发冲突 | 返回 409 和当前版本，用户刷新后重试 |
| 重复命令 | 根据幂等键返回原结果，不重复推进状态 |
| Kafka 不可用 | Outbox 保留并重试；核心事务正常提交 |
| 消费者失败 | 指数退避、幂等重试，永久失败进入死信与人工队列 |
| 模型超时或限流 | 断路、延迟重试或人工升级，不阻塞核心命令 |
| AI 输出无效或无来源 | 拒绝写入有效建议，记录失败原因 |
| Redis 不可用 | 回源数据库或跳过临时能力 |
| 对象存储不可用 | 上传保持待确认，不生成有效证据 |
| Core 或 PostgreSQL 不可用 | Electron 进入只读缓存模式，禁止离线写入 |

## 12. 安全与治理

1. 服务间使用独立身份、最小权限数据库账号和 TLS。
2. 密钥通过环境变量或客户密钥系统注入，不写入领域包、镜像或日志。
3. 权限由 Core 按角色、流程实例、任务归属和动作共同判定。
4. AI 工具白名单不能被检索内容、用户消息或领域包扩大。
5. 客户可配置允许发送给每个模型供应商的数据字段和数据分类。
6. 检索文档视为不可信输入，不能修改系统提示、工具权限或审批规则。
7. AI 生成内容保留明确标记、模型信息、来源和完整追踪记录。
8. 审计记录和证据哈希不能通过普通业务 API 修改或删除。
9. 安装包和更新包必须签名，并从客户授权的更新源分发。
10. 数据备份、保留和删除策略按客户部署配置，并在交付验收中演练恢复。

## 13. 部署与可观测性

每个客户独立部署 Electron 更新源、OCC Core、AI Service、PostgreSQL、Kafka、Redis 和 S3 兼容存储。Docker Compose 提供两种明确配置：

- 试点配置：单节点依赖，适合验证和小规模内部使用，不宣称高可用。
- 生产配置：允许替换为客户已有高可用基础设施；Kafka、PostgreSQL、Redis 和对象存储的副本与恢复目标由客户 SLA 决定。

服务使用结构化日志和统一关联 ID。OpenTelemetry 采集 API、数据库、Kafka 消费和 AI 调用追踪；指标至少覆盖请求延迟、错误率、Flowable 作业、Outbox 积压、Kafka 消费延迟、死信量、Redis 命中率、对象上传失败、AI 首 token 延迟、完整响应延迟、失败率和成本。

## 14. 测试与质量门禁

### 14.1 测试层次

- 领域包：BPMN/DMN、引用、禁用元素、权限、表单和规则回归场景。
- 核心规则：JUnit 5 单元测试和角色 × 资源 × 动作权限矩阵。
- 集成测试：Testcontainers 启动 PostgreSQL、Kafka、Redis 和 MinIO，验证 Flowable、事务、Outbox、幂等、死信和降级。
- 契约测试：OpenAPI 和 Kafka JSON Schema 的提供者/消费者兼容性。
- AI 评测：来源覆盖、结构化输出、工具越权、提示注入、拒答和高风险召回。
- Electron：Vitest、React Testing Library 和 Playwright Electron 端到端测试。
- 发布测试：正式支持的每个 OS/架构执行安装、签名、升级和回滚冒烟测试。

AI 测试断言结构、安全属性和评测指标，不断言模型逐字输出。更换模型、提示词或知识库版本必须重新执行对应评测集。

### 14.2 性能基线

在记录硬件与数据规模的代表性私有服务器配置下，使用 k6 模拟 100 个并发会话：

| 指标 | 基线 |
| --- | --- |
| 缓存命中查询 | p95 不超过 200 ms |
| PostgreSQL 回源查询 | p95 不超过 500 ms |
| 不含文件和 AI 的状态命令 | p95 不超过 700 ms |
| 领域事件到消费者 | p95 不超过 2 s |
| 重试与并发冲突 | 不产生丢失或重复状态转换 |

AI 延迟不纳入核心 API SLA，因为它依赖客户选择的供应商。系统记录首 token、完整响应、失败率和成本，并允许客户配置超时预算。

### 14.3 CI 门禁

格式化、静态检查、单元测试、集成测试、关键 E2E、依赖漏洞检查、许可证清单和 SBOM 均为发布门禁。领域包、桌面安装包和服务镜像保留版本、哈希、签名与构建来源。

## 15. 业务验收关联

技术验收不能替代企划书中的业务验证。首轮试点继续使用以下业务指标：关键节点证据完整率、违规跳步拦截率、重复催办时间下降、等待期任务覆盖率、红色风险漏报、风险误报率、周活跃率和流程修改生效时间。

技术架构成功的判定是：即使关闭 AI Service，流程、任务、证据、审核、风险规则和审计仍能完整运行；启用 AI 后，系统提高建议质量和响应效率，但不改变责任边界。

## 16. 已确认决策与实施前门禁

已确认：

- 所有用户使用 Electron 客户端。
- 每客户独立私有实例。
- 标准 BPMN 由 Flowable 直接执行。
- 接受 JVM Core 与 Node.js AI 双服务。
- LangChain.js 支持多供应商与自定义供应商。
- Kafka 承担跨服务领域事件。
- Redis 承担可重建缓存、AI 缓存和实时状态。
- Electron 断网时仅提供只读缓存。
- 认证同时支持内置账号与 OIDC。
- 跨领域扩展性优先于最短交付路径。

实施开始前必须完成以下门禁：

1. 用一个并行、等待、退回、计时器和人工放行流程验证 Flowable 7.x 与选定 Spring Boot 3.x 精确版本。
2. 冻结首个正式发布的操作系统与 CPU 架构矩阵；未进入矩阵的平台不构成交付承诺。
3. 冻结首个教学领域包的节点表、证据规则、风险规则和一条医学电子模块主路径。
4. 明确试点环境可发送给外部模型的数据分类，并配置默认拒绝策略。
5. 记录用于性能基线的服务器硬件、数据规模和网络条件。
