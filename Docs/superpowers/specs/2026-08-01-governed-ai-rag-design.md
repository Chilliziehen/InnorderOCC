# Governed AI And Authorization-First RAG Design

## Goal

Deliver one production-complete participant-guidance path in which Core remains the authority, AI can use only explicitly authorized knowledge, every recommendation is cited and traceable, and disabling AI never impairs deterministic workflows. The path supports one OpenAI-compatible chat and embedding provider. Other provider families, autonomous workflow mutation, OCR, and general-purpose agent tools are outside this release.

## Selected Approach

The AI service owns a small set of explicit ports for provider transport, persistence, Core exchange, object quarantine, and Kafka. Security-sensitive provider networking is implemented with Node HTTPS and DNS primitives so the service can pin each connection to a validated address, preserve TLS SNI, reject redirects, and prove that credentials never cross origins. PostgreSQL and Kafka use mature clients; LangChain remains optional orchestration glue and does not own transport or authorization.

This is preferred over a provider SDK because SDK redirects, retries, DNS behavior, and telemetry are difficult to constrain. It is preferred over a new egress proxy because an additional privileged service would enlarge deployment and certificate scope without removing the need for application-level origin and capability checks.

## Trust Boundaries

Core is the only end-user entry point and the only writer of provider/source/document heads, recommendations, authorization facts, audit, Outbox, and workflow state. AI accepts only a mutually authenticated Core service certificate on business routes and explicitly rejects bearer credentials. Health remains unauthenticated and contains no configuration details.

Core issues a dedicated RS256 JWT grant with audience `innorder-ai`, type `ai_authorization_grant`, a maximum five-minute lifetime, a unique `jti`, principal, target, purpose, authorization revision, release digest, classification ceiling, authorized-set digest, and task-context digest. Core stores at most 500 authorized document-version IDs plus the bounded canonical task context in immutable grant rows; the JWT never carries either body. More than 500 authorized versions is rejected with `OCC-AI-AUTHORIZED-SET-LIMIT`, never truncated or paged. AI verifies the signature and exact claims, then calls one security-definer function that locks the grant, compares the current authorization revision and both digests, creates or returns the operation's run, marks the grant consumed, and returns the bounded IDs and context. This narrowly delegated consumption is the only AI write in `authz`; it emits no authorization decision and exposes no other authorization facts. Expired, replayed, malformed, or stale-revision grants fail before retrieval.

The `innorder_ai_runtime` login is provisioned outside Flyway from a file-backed secret. Migration V015 grants it only explicit reads of immutable AI configuration/content and bounded writes to AI operational tables. It receives no access to IAM, authorization facts, catalog mutation, OCC/Flowable, audit, Outbox, recommendations, conversations, or Core command tables.

## Data Model

`V016__governed_ai_runtime.sql` extends, but does not rewrite, V007:

- `authz.ai_authorization_grant` and `authz.ai_authorized_document` store token hashes, immutable grant context, and the bounded authorized set; Core inserts and AI can consume only through a hardened function.
- `ai.ingestion_job` stores deterministic parser/chunker versions, object/content hashes, checkpoints, leases, attempts, stage, and sanitized failures.
- `ai.event_consumption` provides durable Kafka event deduplication, retries, leases, and terminal DLQ state.
- `ai.model_invocation` stores request/response hashes, capability snapshot, token/cost totals, latency, status, and sanitized provider identifiers.
- `ai.retrieval_trace` and `ai.retrieval_hit` prove the authorized set and lexical/vector/fused ranking used by each run.
- `ai.embedding_space_gate_result` records coverage, authorization leakage, citation precision, recall at 10, decision, and rollback evidence.

Security-definer functions use a fixed search path and narrow arguments for one-time grant consumption, worker claims, and authorization-filtered hybrid retrieval. Public function execution is revoked. A versioned evaluation dataset must contain at least 20 non-empty cases and a content hash. Coverage is embedded eligible chunks divided by eligible chunks; authorization leakage is the count of returned chunks outside each case's authorized set; citation precision stores supported and total citations for each case and uses the micro-average `sum(supported) / sum(total)`; recall at 10 is expected relevant chunks found in the first ten hits divided by expected relevant chunks and uses a macro-average across cases. Empty denominators fail the gate. Activation requires coverage 1.0, zero leaks, citation precision at least 0.95, and mean recall at 10 at least 0.85, with per-case evidence persisted.

## Provider Adapter

Provider configuration separates one exact HTTPS origin from a fixed normalized API prefix such as `/v1`, and permits optional explicitly approved private CIDRs. URL parsing rejects user info, query strings, fragments, non-HTTPS schemes, ambiguous ports, dot segments, encoded separators, and prefixes that do not start with one slash. Endpoint joining cannot escape the prefix. Hostnames that resolve to loopback, unspecified, link-local, multicast, metadata, documentation, carrier-grade NAT, or private addresses outside approved CIDRs are rejected. Every request resolves all addresses, validates each result, chooses a validated address, and supplies a pinned lookup result to the TLS connection. No redirects are followed.

Credentials are read for each operation from a bounded regular file with strict metadata checks. They are added only after origin validation and are never logged or included in errors. Capability probes call the configured models endpoint and small chat/embedding requests, then persist a normalized snapshot. Profiles cannot become usable unless required capabilities, dimensions, structured output, response limits, and configured models match.

The adapter enforces connect and total timeouts, AbortSignal cancellation, response byte limits, bounded retries only for safe transient failures, per-profile concurrency and token buckets, and deterministic token/cost accounting. Telemetry contains hashes, categories, counts, timing, correlation IDs, and sanitized provider request-ID hashes, never prompts, excerpts, credentials, URLs with query strings, or provider response bodies.

## Ingestion And Retrieval

Uploads enter a quarantine object prefix and create an ingestion job. Production formats are UTF-8 text, Markdown, PDF, DOCX, and XLSX. A signature-updated malware scanner runs before parsing and rejects infected, suspicious, and polyglot input. Parsing runs in a networkless non-root worker with read-only input, a disposable output directory, seccomp/no-new-privileges, one CPU, 512 MiB memory, 60-second wall timeout, 10,000 extracted-entry limit, and 100 MiB expanded-byte limit. The scanner rejects malformed UTF-8, oversize input, MIME/extension mismatch, encrypted files, macros, external relationships, embedded objects, active content, archive bombs, path traversal, and unsupported compression. PDF extraction rejects scripts, attachments, forms, encryption, and pages without extractable bounded text; DOCX and XLSX parsing uses allowlisted Open XML parts with external links and formulas excluded. Parsing normalizes line endings and Unicode, strips transport metadata, and produces deterministic text with page/sheet/section provenance. Chunking uses versioned paragraph-aware boundaries with fixed maximum token count and overlap; each source, normalized document, and chunk is SHA-256 hashed. Executable fixtures cover malware, polyglots, bombs, traversal, active content, and resource exhaustion for every supported container format.

Jobs checkpoint after scan, parse, chunk, and embed stages and are safe to reclaim after a lease expires. A failed build never changes the current document head or ACTIVE embedding space. Gate evidence is bound to a digest of every eligible document version/chunk hash, the candidate space, and the expected current ACTIVE space. After AI records passing gates, Core executes an idempotent activation command that locks and rechecks the manifest digest, immutable gate evidence, and expected ACTIVE space before atomically changing the document head and embedding-space statuses. Any intervening head or corpus change rejects activation. Rollback is another Core command that restores the previous eligible version/space without deleting trace data. AI has no direct update privilege on document heads or activation state.

Core authorizes document entities and a bounded task-context projection under one locked authorization snapshot and places only authorized document-version IDs in the grant rows. Task context contains only task ID, title, state, blocker codes, evidence requirement labels, and package version, is capped at 32 KiB canonical JSON, and is persisted by hash. AI materializes the authorized ID set before any content query. The hybrid SQL joins candidates to that set in both full-text and vector CTEs, applies the grant's classification ceiling, normalizes ranks, and uses reciprocal-rank fusion with deterministic UUID tie-breaking. Classification order is `PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED`; chunks inherit the document version. The selected provider profile declares its maximum accepted classification, and the run is denied before any provider call when task context or a selected chunk exceeds it. Empty authorized sets produce no provider call.

## Guidance Run

The participant-guidance agent is bound to one published prompt version, package version, strict input schema, and strict output schema. Retrieved excerpts are encoded as untrusted citation blocks and the system prompt states that block instructions are data, not commands. The first release exposes no model tools.

The model must return `generatedContent: true`, a recommendation summary, ordered guidance steps, confidence, and citations containing retrieval-hit IDs and excerpt hashes. The schema contains no workflow command, policy decision, completion, grade, or authorization fields. Ingestion marks instruction-like source spans, including attempts to override prompts, reveal secrets, change authorization, bypass gates, disable controls, or execute tools. A run rejects guidance that cites a marked span as normative instruction, contains a normalized prohibited bypass/security-disable intent, or differs from the fixed expected safe outcome in adversarial evaluation cases. Unknown fields, malformed JSON, any `generatedContent` value other than `true`, citations outside the run, excerpt hash mismatches, duplicate ranks, or a guidance step without at least one citation also fail the run. Adversarial fixtures cover every supported format and produce either `OCC-AI-PROMPT-INJECTION` or an explicitly versioned safe recommendation. Valid output persists the run, invocation, retrieval trace/hits, output artifact hash, and evaluations before AI submits a bounded recommendation command to Core over mTLS.

Core revalidates the service identity and run payload, creates the recommendation and citation rows transactionally, and emits an Outbox event. Guidance is informational and cannot encode a domain command. Human accept/reject is itself a normal `ReviewRecommendationCommand` with the current human principal, fresh OPA decision, idempotency key, and expected recommendation version; acceptance records review state but does not advance workflow. Any later participant workflow action is a separate fresh command. AI credentials and the historical grant cannot execute either command.

## APIs And Events

Core exposes versioned provider profile/probe, knowledge upload/status/activate/rollback, guidance request/status, recommendation list/detail, and recommendation review endpoints. Every mutation requires `Idempotency-Key`; every update also requires `expectedVersion`. Stable retries return the original result. Core performs current OPA authorization and classification checks for every recommendation list item, detail, citation, and review response; an authorization or relationship change denies or redacts previously visible restricted content. Lists use bounded cursor pagination; errors use existing Problem Details conventions.

Kafka is the sole work trigger. Core commits the operation and a `guidance-requested` Outbox event containing only the non-secret operation ID. AI durably claims that event, then calls a Core mTLS grant-claim endpoint with the operation ID; Core returns the single-use JWT only to the AI certificate identity. The grant-consumption transaction links the event, operation, and run, so endpoint retry and Kafka replay return the same state without a second provider call. AI-to-Core mTLS endpoints submit a recommendation and report ingestion/probe outcomes; Core-to-AI mTLS exposes only status/cancellation queries. These routes are not exposed through Caddy and each direction accepts only the expected certificate identity. Events use the existing envelope and add versioned knowledge-ingestion-requested, guidance-requested, recommendation-proposed, and AI-operation-dead-lettered payloads. AI persists an event ID before work, acknowledges duplicates without repeating side effects, retries with bounded backoff, and records terminal DLQ state for operator replay.

When `AI_ENABLED=false`, Core does not enqueue AI work, AI readiness reports disabled, and recommendation actions are absent. The same degradation applies when AI readiness, Kafka delivery, or the selected provider remains unavailable beyond its bounded probe window. Existing recommendations are presented stale when their package, policy release, document versions, provider capability snapshot, target version, or AI availability state no longer matches. Recovery requires fresh readiness and capability probes and never automatically resubmits a human request. Authentication, authorization, workflow, evidence, review, risk, resource, and administration behavior remains unchanged.

## Deployment

Compose adds file-backed AI database, provider, and Core/AI mTLS secrets. Core and AI certificates contain fixed service identities and use deployment CA trust stores. Certificates rotate with a 24-hour overlap; trust bundles accept current and next issuers, revocation removes an identity without rebuilding images, and expired, revoked, wrong-EKU, wrong-SAN, or wrong-service certificates fail integration tests. AI remains on the internal backend network. Optional provider access is routed through a dedicated AI-only egress network while application-level exact-origin validation remains mandatory. PostgreSQL provisions `innorder_ai_runtime` before Flyway; Core and AI never share database credentials.

## Failure Semantics

All authorization, identity, capability, classification, parsing, embedding, citation, and provider-boundary failures are closed failures with stable sanitized codes. Cancellation releases leases and sockets but preserves immutable trace records. Provider outage, Kafka replay, AI restart, or a failed embedding build cannot mutate authoritative workflow state or remove the previous active index. Grant consumption and initial run creation are one transaction. Retries after consumption resume only persisted stages of that run and cannot expand its authorized set; duplicate pre-consumption events return the existing operation, while a new retrieval requires Core to issue a new grant under a fresh snapshot.

AI run traces, recommendation citations, invocation accounting, retrieval traces, and gate evidence are retained for one year by default and participate in legal hold. Raw quarantined uploads are deleted after successful activation or 30 days after terminal failure unless held; transient provider bodies are never persisted. Backup and restore include V015 tables, pgvector partitions, active/previous space metadata, immutable prompt/evaluation versions, and held quarantine objects. Restore acceptance proves recommendation trace integrity and retrieval readiness without contacting a provider.

## Verification

TDD proceeds from contracts and database boundaries through provider transport, ingestion/retrieval, agent validation, Core commands, async behavior, and deployment. Unit tests cover strict schemas, deterministic parsing/chunking, URL/IP policy, capability matching, output/citation validation, accounting, cancellation, and disabled behavior. PostgreSQL tests use real pgvector and the real AI login to prove both allowed operations and denied cross-schema access. Provider-stub tests cover DNS/private-address rejection, no redirects, timeouts, malformed bodies, capability mismatch, cancellation, response limits, and credential non-forwarding.

Mandatory integration tests exercise Core, AI, mTLS, OPA, PostgreSQL/pgvector, Kafka, and the provider stub for authorized success plus unauthorized IDs, stale/replayed grants, injected instructions, malformed/uncited output, failed builds, provider failure, Kafka replay/DLQ, recommendation review, fresh-command acceptance, and AI-disabled workflows. `verify:full` validates structured results with no skips or failures. The baseline quick gate currently has a pre-existing failure because `PlatformSecurityKernelIntegrationTest` requires `OPA_PATH` even outside full mode; the implementation plan includes correcting that test selection contract before using quick verification as a regression gate.
