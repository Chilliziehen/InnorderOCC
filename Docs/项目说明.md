# 创序 OCC 项目说明

> Innorder Operation Control Center — 流程可执行、责任可追溯、智能可治理的运营控制中心

| 项目 | 内容 |
|---|---|
| 项目名称 | 创序 OCC（Innorder OCC） |
| 仓库 | `InnorderOCC` |
| 交付形态 | 每客户独立私有部署（Docker Compose 单主机栈）+ Electron 桌面客户端 |
| 首发领域 | 嵌入式开发教学；内核不绑定具体行业，通过领域包扩展 |
| 文档版本 | 2026-08 |

## 一、项目概述

### 1.1 我们解决什么问题

在需要「按规范推进、留痕可查、责任清晰」的运营场景里，组织普遍面临三类问题：

1. **流程靠人记、靠群里催**。节点顺序、前置条件、证据要求散落在文档和口头约定中，跳步和漏做无法被系统拦截。
2. **过程无法举证**。谁在什么时间、基于什么依据、做了什么决定，事后无法完整复原。
3. **AI 用不敢用**。大模型能提效，但把它接入关键流程后，没人能保证它不会越权改状态、不会胡编依据、不会把敏感数据发出去。

创序 OCC 针对这三点给出的答案是：**用标准 BPMN 把流程变成可执行的确定性程序，用统一授权内核和不可变审计把责任固定下来，用受治理的 AI 层把智能能力约束在"只建议、不落笔"的边界内。**

### 1.2 核心设计理念：双轨架构

系统由两个性质完全不同的面组成，边界由代码强制，而不是靠约定：

- **确定性控制面（Deterministic Plane）**
  标准 BPMN 流程由 Flowable 引擎直接执行，全部业务状态只能由 OCC Core 在 PostgreSQL 事务中推进。流程走到哪、任务归谁、证据够不够、能不能放行，全部由规则和数据决定，可重放、可验证。

- **概率智能面（Probabilistic Plane）**
  AI 服务承担理解、检索、规划、核验和风险预警，产出的是**建议**和**待核验结论**，必须经过 Core 的授权、校验和人工/规则确认才能影响事实。

> **架构成功的判定标准：把 AI 服务整个关掉，流程、任务、证据、审核、风险规则和审计依然完整运行。** 开启 AI 后系统提升建议质量和响应效率，但不改变任何一条责任边界。

### 1.3 产品特征

| 特征 | 说明 |
|---|---|
| 标准 BPMN 驱动 | 不自研流程引擎，用行业标准建模，流程资产可迁移、可审计 |
| 领域包扩展 | 换行业只需发布新的版本化领域包，不复制修改核心服务 |
| 全链路留痕 | 每次状态变更都写入不可变审计记录，含操作者、依据、前后版本 |
| 授权内核统一 | 所有敏感操作走同一条授权路径：事务快照 → OPA 决策 → 决策落库 |
| AI 可治理 | 工具白名单、结构化输出校验、来源强制引用、数据分类出境控制 |
| 私有部署 | 单客户独立实例，数据不出客户机房，支持接入客户已有基础设施 |
| 桌面统一入口 | 一个安装包按权限呈现十个工作区，断网时降级为只读缓存 |

## 二、系统架构

### 2.1 总体拓扑

```text
                    ┌─────────────────────────────┐
                    │   Electron 桌面客户端        │
                    │   React + TypeScript + AntD  │
                    └──────────────┬──────────────┘
                                   │ HTTPS / REST + SSE
                                   │ JWT 会话，受限 preload IPC
                                   ▼
        ┌──────────────────────────────────────────────────┐
        │        OCC Core (Kotlin + Spring Boot + Flowable) │
        │  api │ auth │ authz │ command │ events │ iam      │
        │  process │ task │ evidence │ risk │ resource      │
        └───┬────────┬─────────┬──────────┬────────┬────────┘
            │        │         │          │        │
            ▼        ▼         ▼          ▼        ▼
      PostgreSQL   OPA       Redis     S3/MinIO   Outbox
      + pgvector  (决策)    (缓存)    (证据文件)    │
      业务事实                                      │
      流程数据                                      ▼
      审计/Outbox                                 Kafka
      向量索引                                      │
                                                   ▼
                              ┌────────────────────────────────┐
                              │  AI Service (Fastify + LangChain)│
                              │  规划 │ 辅导 │ 核验 │ 风险 │ 监督 │
                              └────────────────────────────────┘
```

### 2.2 所有权边界（架构硬约束）

这是整套系统最核心的约束，所有代码评审、设计变更都以此为准绳：

| 组件 | 允许做什么 | 禁止做什么 |
|---|---|---|
| **Desktop** | 通过受限 preload IPC 调用 Core 的领域 API | 直连 PostgreSQL / OPA / Flowable；直接改变业务状态；调用 Flowable 原生 API |
| **Core** | 唯一的事实与状态转换所有者，封装 Flowable，协调授权决策 | 向外暴露 Flowable 原生对象、表名或内部状态编码 |
| **AI** | 生成能力描述、建议、待核验结论；通过受限命令 API 提交 | 直接写事实、调用 Flowable、绕过 Core 执行变更、读取 Core 业务表 |
| **PostgreSQL** | 结构化业务事实的唯一权威来源 | — |
| **OPA** | 基于 Core 提供的事实做无状态允许/拒绝决策 | 保存或修改任何业务事实 |
| **Redis** | 可重建的读缓存、AI 缓存、限流、在线状态 | 承载不可重建数据；与 PG 做双写事务 |
| **Kafka** | 跨服务领域事件投递 | 直接推进 Flowable 关键状态；作为业务事实主存储 |

### 2.3 正确性模型

系统**不承诺** PostgreSQL 到 Kafka 的端到端 exactly-once，采用工业界成熟的组合方案：

```
Transactional Outbox（事务内写事件）
    + 至少一次投递（Outbox Publisher 重试）
    + 聚合内有序（Kafka 分区键 = 业务聚合 ID）
    + 消费者幂等（按事件 ID 去重）
    = 可证明的最终一致
```

命令侧的并发控制：

- **幂等键（Idempotency-Key）**：重复提交返回原结果，不重复推进状态。
- **`expectedVersion` 乐观锁**：版本不匹配返回 `409 Conflict` 与当前版本，客户端必须刷新后重试，绝不静默覆盖。
- **规范化 JSON（Canonical JSON）**：命令载荷规范化后参与幂等指纹计算，避免字段顺序造成的误判。

## 三、功能模块

### 3.1 身份与访问（IAM / Auth）

- **内置账号 + OIDC 双通道**。本地试点用内置账号快速起步，企业环境接入客户身份平台。
- **会话与令牌**：Core 签发短时访问令牌，会话状态落库可吊销；失败登录进入滑动时间窗计数，达到阈值锁定。
- **OIDC 流程走系统浏览器**，回调经受控深链接返回 Electron；令牌由主进程用操作系统安全存储保管，**不进入渲染进程的持久存储**。
- **管理员引导**：首次部署通过文件型密钥引导初始管理员，凭据不入镜像、不入仓库、不入日志。

### 3.2 统一授权内核（Authorization Kernel）

这是整个系统的安全支点，也是投入最重的部分之一。

**决策链路**：

```
业务命令
  → 事务内取授权快照（authz.authorization_state FOR SHARE / FOR UPDATE）
  → 构造 principal / action / resource / entity / relationship / context 输入
  → 调用本地 OPA（Rego 策略，已发布版本）
  → 校验响应中的 policy_release 与 authorization_revision 与快照一致
  → 写入 authz.decision_log（分区表，不可变）
  → 允许则继续事务，拒绝则整体回滚
```

**关键性质**：

- **默认拒绝**：无匹配规则一律拒绝。
- **显式拒绝优先**：任何适用的 DENY 覆盖所有 ALLOW。
- **决策一致性防护**：Core 拒绝接受策略版本或授权 revision 与事务快照不一致的 OPA 响应，从根本上消灭 TOCTOU 窗口。
- **关系闭包只是投影**：`authz.relationship_closure` 是可重建的查询加速表，**永远不作为最终 allow 事实**——OPA 收到的始终是直接关系。
- **策略发布完整性**：策略 bundle 带内容哈希与版本，发布记录不可变，支持回滚。
- **决策理由结构化**：返回 `reason_codes`（`EXPLICIT_DENY` / `PRINCIPAL_DISABLED` / `RESOURCE_INACTIVE` / `ACTION_FORBIDDEN` / `NO_MATCHING_ALLOW` / `ALLOW_GRANT_MATCH`）与 `reason_ids`，既能给用户可理解的说明，又能给审计留下精确依据。

### 3.3 命令执行内核（Command Kernel）

所有改变状态的操作走同一条通道，保证行为一致：

```
CommandExecutor
  ├─ 载荷规范化与大小限制
  ├─ 幂等键查重（命中即返回原结果）
  ├─ 授权决策（3.2）
  ├─ expectedVersion 乐观锁检查
  ├─ 业务规则与 Flowable 执行
  ├─ 业务表写入
  ├─ 审计记录写入（audit.audit_record，分区，不可变）
  └─ Outbox 事件写入
        ── 同一数据库事务提交 ──
```

事务边界由启动期校验器（`FlowableTransactionBoundaryVerifier`）强制检查，确保 Flowable 操作与业务写入处在同一事务管理器下，杜绝"流程走了、业务没落库"的错位。

### 3.4 流程与任务（Process & Task）

- **流程定义**：BPMN/DMN 部署与版本管理，Flowable 适配层完全封装在 Process 模块内部。
- **流程实例**：生命周期管理、业务键、**显式绑定领域包版本**——发布新版本不影响运行中的实例。
- **实例迁移**：作为独立的授权操作执行，必须先生成影响预览，并经授权人员确认。
- **任务**：人工任务、候选人组、领取/退回/转办、完成、期限、例外处理。
- **支持完整 BPMN 语义**：并行网关、排他网关、等待状态、计时器边界事件、补偿、人工放行。
- **今日任务视图**：按人聚合的待办，含期限、优先级和阻塞原因。

### 3.5 证据管理（Evidence）

证据是"可举证"的物理载体，链路设计为不可伪造：

1. 客户端向 Core 申请**短时上传许可**。
2. 客户端直传对象存储，同时提交客户端计算的哈希。
3. Core 校验对象存在性、大小、类型与哈希一致性。
4. Core 在事务中创建证据元数据并关联任务。
5. 未完成或未关联的孤儿对象由后台任务按保留策略清理。

**只有 Core 校验并提交元数据后，文件才构成有效证据。** 证据记录与哈希不可通过普通业务 API 修改或删除。支持版本化：同一证据位可多次提交，历史版本全部保留。

### 3.6 风险管理（Risk）

- **规则驱动**：触发条件、风险等级、责任人、处置时限、升级对象全部在领域包中声明。
- **风险雷达**：按等级和时限聚合的实时视图，红色风险独立跟踪。
- **AI 增强**：AI 可以生成风险建议并写入队列，但风险的定级与关闭始终由规则或授权人员决定。
- **闭环追踪**：从触发、认领、处置到关闭，全过程留痕。

### 3.7 资源管理（Resource）

设备、场地、人员时段的容量与预约。资源冲突检测基于数据库排他约束（`btree_gist`），在存储层保证不会出现双重预定。

### 3.8 领域包（Domain Package）

领域包是**跨领域扩展的最小发布单元**，也是产品化能力的关键。

一个领域包包含：

| 内容 | 说明 |
|---|---|
| `manifest` | 领域标识、语义版本、依赖、内容哈希、兼容范围 |
| BPMN | 流程、人工任务、服务任务、事件、网关、计时器 |
| DMN | 确定性准入、风险分级、条件判断 |
| JSON Schema 表单 | 节点输入、审核、配置表单 |
| 角色与权限 | 领域角色到 OCC 动作的映射 |
| 证据规则 | 允许类型、大小、数量、哈希、验收条件 |
| 风险规则 | 触发条件、等级、时限、升级对象 |
| 知识源清单 | 来源、版本、访问策略、索引参数 |
| UI 元数据 | 标签、排序、分组、领域展示信息 |
| 回归场景 | 发布前必须通过的标准流程与规则样例 |

**安全约束**：领域包**不允许携带任意可执行脚本、数据库迁移或密钥**。扩展服务任务只能引用核心预注册的受控能力标识——这条约束把"配置化扩展"和"任意代码执行"彻底隔开。

**生命周期**：草稿 → 已校验 → 已发布 → 已废弃。已发布版本不可修改，具有内容哈希。

**发布流程**：编辑 → Core 校验语法/引用完整性/禁用元素/权限/回归场景 → 生成版本差异与运行实例影响预览 → 授权人员确认 → 固化内容与哈希 → 部署 Flowable 定义。

### 3.9 受治理的 AI 层（Governed AI）

AI Service 是独立进程，内部包含规划、辅导、核验、风险、监督五类 Agent，共享模型适配、工具注册、结构化输出校验、RAG、追踪和评测设施，**但不共享可变的私有业务事实**。

**多供应商接入**：

- 基于 LangChain.js，支持内置供应商与 OpenAI 兼容的自定义端点。
- 每个供应商配置声明：模型能力、**允许发送的数据分类**、超时、并发、限流、成本元数据。
- **能力不足即拒绝**：模型不支持所需能力（如结构化输出、工具调用）时，服务拒绝执行，而不是降级为不可验证的输出。
- 传输层强制安全配置，凭据从文件型密钥读取，不落日志。
- 内置限流器、重试策略、成本核算。

**RAG 与知识治理**：

- 知识源版本化，检索结果**必须带版本化来源引用**。
- 向量存储基于 pgvector，embedding space 显式声明维度与距离度量，分区表 + HNSW 索引。
- **检索文档视为不可信输入**：不能修改系统提示、扩大工具权限或改变审批规则。

**安全约束（提示注入防线）**：

1. Agent 工具采用**白名单**，输入输出用 Zod 强校验。
2. **工具白名单不能被检索内容、用户消息或领域包扩大**。
3. 关键建议必须记录：客户实例、模型、提示词版本、领域包版本、知识库版本、引用来源、工具调用链、最终结构化结果。
4. AI 生成内容保留明确标记，用户始终知道哪些内容来自模型。
5. **无有效来源的输出不写入建议**，记录失败原因。

**缓存规则**：AI 缓存键必须包含客户实例、领域包版本、知识库版本、供应商、模型名、提示词版本。**禁止缓存**流程准入结论、证据有效性、审批结果、权限判定结果和未提交状态。

### 3.10 桌面客户端（Desktop）

同一个安装包按权限呈现十个工作区：

| 工作区 | 内容 |
|---|---|
| 总览 Overview | 运行指标、服务状态、活动流程摘要 |
| 我的工作 MyWork | 今日任务、待办、期限提醒 |
| 流程 Processes | 流程地图、实例详情、执行轨迹 |
| 人工介入 Interventions | 异常、审批、策略阻断的统一队列 |
| 风险 Risks | 风险雷达、分级跟踪、处置闭环 |
| 资源 Resources | 设备、场地、时段的容量与预约 |
| 领域建模 DomainDesign | BPMN 编辑（bpmn-js）、领域属性配置、发布预览 |
| 管理 Administration | 用户、角色、权限、策略发布 |
| 系统运维 SystemOperations | 依赖状态、Outbox 积压、决策日志检索 |
| 设置 Settings | 连接配置、本地档案、偏好 |

**Electron 安全基线**：

- 渲染进程启用 sandbox、context isolation、CSP，**关闭 Node 集成**。
- 文件系统、更新、深链接、凭据操作**仅由主进程执行**，通过有类型约束的 preload IPC 暴露最小接口。
- 导航策略白名单，阻止任意外部导航与新窗口。
- IPC 载荷有序列化大小上限，防止渲染进程通过超大载荷影响主进程。
- **离线降级**：Core 不可达时进入只读缓存模式，所有变更操作明确禁用——**不接受离线写入，不做冲突合并**。

### 3.11 通知与实时（Notifications）

可靠通知**先持久化再推送**：事件落库后通过 SSE 推送在线客户端，离线用户上线后按游标补齐。Redis 只承载在线连接映射和短期游标，丢失不影响通知可达性。

### 选型说明：为什么是这套

| 备选 | 结论 | 理由 |
|---|---|---|
| **Flowable 嵌入式模块化平台** | ✅ 采用 | Apache 2.0 许可可私有部署；流程事务与业务事务可在同一服务边界内协调；组件数量适合小团队长期维护 |
| Camunda 8 分布式编排 | ❌ 未采用 | 自托管生产需企业许可，完整组件栈对当前规模过重。仅在客户明确承担许可成本且出现大规模分布式编排需求时重新评估 |
| 全 TypeScript 自研 BPMN 层 | ❌ 未采用 | 定时器、并发网关、补偿、迁移、幂等、历史审计、异常恢复将全部成为自研责任，而这些恰好位于最要求确定性的控制内核 |

代价是同时维护 JVM 与 Node.js 两个运行时，以及自研领域化工作台。通过 OpenAPI 契约、版本化事件 schema 和严格数据库边界来控制这部分复杂度。

## 五、数据模型

### 5.1 Schema 划分

八个 schema，通过 Flyway 顺序迁移（V001–V015）建立，职责严格分离：

| Schema | 内容 |
|---|---|
| `platform` | 组织实例配置、平台级参数、数据策略 |
| `catalog` | 目录与字典数据 |
| `iam` | 用户、角色、成员关系、身份映射、会话 |
| `authz` | 授权实体、关系图、关系闭包投影、策略发布、决策日志（分区） |
| `occ` | 运行时业务事实：流程实例、任务、证据、风险、资源 |
| `audit` | 审计记录（分区） |
| `ai` | 知识源、embedding space、向量分区、AI 运行与建议记录 |
| `flowable` | 由 Flowable 引擎自行创建维护 `ACT_*` 表 |

### 5.2 核心实体

| 实体 | 关键内容 |
|---|---|
| Organization Instance | 私有部署的组织配置与数据策略 |
| User / Role / Membership | 用户、领域角色、组织关系、身份映射 |
| Domain Package / Version | 领域资产、状态、哈希、兼容范围、发布记录 |
| Process Definition / Instance | Flowable 标识、业务键、领域包版本、生命周期 |
| Task | 类型、状态、负责人、候选人、期限、版本 |
| Evidence | 对象引用、类型、大小、哈希、提交人、验收记录 |
| Event | 状态变化、原因、关联 ID、操作者、发生时间 |
| Risk | 等级、规则、置信度、责任人、时限、处置结果 |
| Resource | 设备、场地、人员时段、容量、预约 |
| AI Run / Recommendation | 模型、提示词、来源、工具调用、结果、审核状态 |
| Audit Record | 操作者、动作、对象、前后版本、理由、时间 |
| Outbox Record | 事件载荷、schema 版本、发布状态、重试信息 |

### 5.3 数据库层的强约束

- **双角色隔离**：`innorder_flyway` 拥有 schema 并执行迁移；`innorder_runtime` 只获得 DML 与序列权限。对 `flowable` schema 仅授予 `USAGE, CREATE`，让 Flowable 拥有自己的 `ACT_*` 表而不拥有 schema 本身。
- **授权事务锁**：普通授权敏感写入前 `SELECT current_revision FROM authz.authorization_state WHERE singleton FOR SHARE`；改动关系、策略发布或实体授权属性时改用 `FOR UPDATE`，由 schema 触发器递增 revision。
- **不可变行**：已发布的领域包、策略、证据、文档版本、消息、审计和决策记录，由触发器保证不可修改。
- **前向迁移**：核心 schema 变更只允许 forward-only Flyway 迁移。领域包可新增版本化定义和 JSONB 数据，**但不能执行 DDL**。
- **分区日志**：`authz.decision_log` 与 `audit.audit_record` 按范围分区并保留默认分区，任何日期都可写入；生产运维提前创建月度分区。
- **向量分区**：`ai.create_embedding_partition(space_id, dimensions, metric)` 校验维度与距离度量、创建 list 分区、加维度检查、建匹配的 HNSW 索引。同一时刻只允许一个 embedding space 处于 `ACTIVE`。
- **Core 与 AI 使用独立 schema 和独立数据库账号**，AI 不能读取 Flowable 表或 Core 业务表。

## 六、API 与契约

- **同步命令与查询走 HTTPS REST**，OpenAPI 规格（`packages/contracts/openapi/occ-core.yaml`）是 Desktop、Core、AI 三方的契约来源。
- **共享类型**：`@innorder/contracts` 用 Zod 定义并导出运行时校验器与 TypeScript 类型，覆盖 auth、authorization、process、task、evidence、risk、resource、events、notifications、governed-ai、system-status、problem-details。
- **错误响应统一用 Problem Details**（RFC 9457 风格），包含稳定错误码、可重试属性、关联 ID 和用户可理解说明。
- **关联 ID 全链路透传**：`x-correlation-id` 从桌面发起，贯穿 Core、OPA 决策、Outbox 事件、Kafka 消费与 AI 调用。
- **Unicode 规范化**：所有文本输入统一规范化处理，防止同形字与不可见字符造成的绕过。
- **Kafka 事件使用带版本的 JSON Schema**，CI 阻止未提供兼容策略的破坏性变更。
- **事件信封**包含：事件 ID、schema 版本、客户实例 ID、聚合类型、聚合 ID、聚合版本、发生时间、关联 ID、数据分类。
- **事件载荷策略**：`EventPayloadPolicy` 在发布前检查载荷不含被禁止的敏感字段类别。

## 七、安全与治理

### 7.1 安全基线

1. 服务间使用独立身份、**最小权限数据库账号**和 TLS。
2. 密钥通过环境变量或客户密钥系统注入，**不写入领域包、镜像或日志**。
3. 授权在事务快照内完成，任何适用拒绝覆盖允许，无匹配默认拒绝。
4. AI 工具白名单不能被检索内容、用户消息或领域包扩大。
5. 客户可配置允许发送给每个模型供应商的数据字段与数据分类。
6. 检索文档视为不可信输入，不能修改系统提示、工具权限或审批规则。
7. AI 生成内容保留明确标记、模型信息、来源和完整追踪记录。
8. 审计记录与证据哈希不能通过普通业务 API 修改或删除。
9. 安装包与更新包必须签名，从客户授权的更新源分发。
10. 数据备份、保留和删除策略按客户部署配置，并在交付验收中演练恢复。

### 7.2 供应链来源控制

这是本项目区别于一般业务系统的一块重点投入：

- **Electron 二进制**只使用官方 GitHub Releases 的固定版本源与校验和，仓库不配置第三方镜像或下载覆盖变量。来源检查递归覆盖所有已提交的可执行与配置源码（含 `vendor/`）。
- **`npm run install:verified`** 不依赖已有 `node_modules`：先拒绝继承环境与仓库配置中的镜像、自定义下载源和校验覆盖，再用官方 registry 与仓库内可写缓存执行 `npm ci`。
- **容器镜像**（外部镜像与 Dockerfile 基础镜像）全部固定可读 tag + `sha256` digest。
- **JVM 依赖**：Gradle 始终以 strict dependency verification 校验签入的 artifact checksum 与签名元数据。
- **发布制品**：领域包、桌面安装包和服务镜像均保留版本、哈希、签名与构建来源。

## 八、部署与运维

### 8.1 部署形态

每客户独立部署一整套：Electron 更新源、OCC Core、AI Service、OPA、PostgreSQL、Kafka、Redis、S3 兼容存储。

Compose 提供两种明确配置：

- **试点配置**：单节点依赖，适合验证与小规模内部使用。
- **生产配置**：允许替换为客户已有的高可用基础设施；Kafka、PostgreSQL、Redis 和对象存储的副本与恢复目标由客户 SLA 决定。

### 8.2 端口与状态路由

| 服务 | 默认主机端口 | 状态或主要路由 |
|---|---:|---|
| Core | `8080` | `/actuator/health/readiness`、`/api/v1/system/status` |
| AI | `3100` | `/health`、`/api/v1/system/status`、`/api/v1/providers/capabilities` |
| OPA | `8181` | `/health`、`/v1/data/innorder/platform/authz/decision` |
| PostgreSQL | `5432` | PostgreSQL 协议 |
| Kafka | `9092` | Kafka 协议 |
| Redis | `6379` | Redis 协议 |
| MinIO API / Console | `9000` / `9001` | `/minio/health/ready` |

Compose 发布端口全部绑定 `127.0.0.1`，容器间通过内部 `backend` 网络通信。

Core 统一上报依赖状态：`postgresql`、`flowable`、`opa`、`kafka`、`redis`、`minio`，状态枚举为 `READY / DEGRADED / UNREACHABLE / CHECKING`，任一依赖非 READY 时整体降为 `DEGRADED`。桌面据此渲染服务状态面板。

### 8.3 密钥管理

**凭据绝不写进 `.env`、Compose 文件或仓库。** 实际做法：

1. 在仓库外创建**八个各含单一非空值的独立文件**（三个 PostgreSQL 密码互不相同，MinIO 应用账号与 root 凭据不同）。
2. `infra/compose/.env` 中**只填这八个文件的绝对路径**。
3. 先执行 Compose 插值验证，确认镜像 tag 与 digest 保留，再构建启动。

```powershell
Copy-Item infra/compose/.env.example infra/compose/.env
docker compose --env-file infra/compose/.env -f infra/compose/compose.yml config
docker compose --env-file infra/compose/.env -f infra/compose/compose.yml up --build
```

### 8.4 可观测性

- 结构化日志 + 统一关联 ID。
- OpenTelemetry 采集 API、数据库、Kafka 消费和 AI 调用的追踪。
- 指标覆盖：请求延迟、错误率、Flowable 作业、Outbox 积压、Kafka 消费延迟、死信量、Redis 命中率、对象上传失败、AI 首 token 延迟、完整响应延迟、失败率与成本。

### 8.5 故障处理与降级矩阵

| 故障 | 系统行为 |
|---|---|
| 并发冲突 | 返回 409 与当前版本，用户刷新后重试 |
| 重复命令 | 按幂等键返回原结果，不重复推进状态 |
| Kafka 不可用 | Outbox 保留并重试，核心事务正常提交 |
| 消费者失败 | 指数退避、幂等重试，永久失败进入死信与人工队列 |
| 模型超时或限流 | 断路、延迟重试或人工升级，不阻塞核心命令 |
| AI 输出无效或无来源 | 拒绝写入有效建议，记录失败原因 |
| Redis 不可用 | 查询回源 PostgreSQL，临时能力降级 |
| 对象存储不可用 | 上传保持待确认，不生成有效证据 |
| Core 或 PostgreSQL 不可用 | 桌面进入只读缓存模式，禁止离线写入 |
